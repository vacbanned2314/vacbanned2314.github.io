# Инструкции Claude Code для сайта «ТеплоРемСервис»

## С чего начинать

Перед любой задачей прочитай:

1. `AGENTS.md` — общие правила проекта и обязательный порядок браузерной проверки.
2. `DESIGN.md` — действующий визуальный язык и существующие рецепты компонентов.
3. Страницу, которую нужно изменить, её подключённые CSS-файлы и связанные JS-модули.

`AGENTS.md` и `DESIGN.md` — источники истины. Не заменяй их собственной дизайн-системой и не создавай параллельные правила.

## Контекст проекта

Это статический русскоязычный сайт инженерной компании по монтажу и обслуживанию отопления, котельных и автоматики. Стек — HTML, CSS и vanilla JavaScript без фреймворка.

Главная задача сайта — получить обращение на установку или обслуживание и одновременно доказать компетентность компании. Поэтому ясность услуг, реальные фотографии, документы, команда, понятные контакты и доверие важнее декоративных эффектов.

Основные страницы: `index.html`, `services.html`, `portfolio.html`, `team.html`, `licenses.html`, `faq.html`, `privacy.html`.

## Правила принятия решений

- Перед существенным изменением изучи существующую реализацию и сначала объясни, что именно меняешь и почему.
- Если задача подразумевает несколько существенно разных вариантов структуры, UX или визуального направления, остановись и предложи 2–3 конкретных направления с различиями. Не выбирай важное направление молча.
- Небольшие исправления очевидного дефекта можно реализовать сразу, если они не меняют продуктовую логику или визуальное направление.
- Не выдумывай цены, сроки, гарантии, допуски, клиентов, адреса, отзывы, характеристики оборудования или другие факты. Если данных нет, оставь существующий текст или вынеси вопрос пользователю.
- Не переписывай страницу целиком без необходимости. Сохраняй работающие ссылки, формы, SEO-разметку, доступность и существующую информационную архитектуру.

## Визуальный язык

- Используй `Golos Text` и существующую типографическую шкалу из `css/variables.css`.
- Основной визуальный мир — тёмная сталь, графит, эмаль и один медно-огненный акцент. Медный цвет означает действие, активное состояние или важный факт, а не декоративную заливку.
- Используй семантические токены из `:root` в `css/variables.css` (`--surface-*`, `--text-*`, `--accent`, `--accent-fill`, `--border-*`, `--status-*`, `--trs-*`), а не новые произвольные hex-цвета.
- Новые кнопки, панели, поля, фильтры и технические подписи собирай из существующих рецептов в `css/unified-components.css`, `css/base.css` и `css/variables.css`.
- Контент размещай в `.container`, для разделов используй существующий вертикальный ритм и не вводи локальную сетку без причины.
- Соблюдай существующие радиусы, тонкие границы, спокойные тени и `--trs-ease`. Не добавляй стеклянные панели, свечение, декоративные градиентные пятна, псевдочертежи и «технические» подписи без смысла.
- Реальные фотографии портфолио, сотрудников и документы — доказательства работы. Не заменяй их AI-изображениями, не подменяй содержимое фильтрами и не создавай фальшивые доказательства.
- Не превращай сайт инженерной компании в generic SaaS-лендинг с одинаковыми карточками, метриками и декоративными bento-блоками.

## HTML, CSS и JavaScript

- Сначала переиспользуй существующие классы и общий слой стилей. Если паттерн повторяется на трёх и более страницах, вынеси его в общий CSS, а не копируй page-specific правила.
- Следи за порядком CSS-импортов и каскадом. `scripts/build-site.mjs` собирает page CSS в production-бандлы; не редактируй сгенерированный `dist/` вручную.
- Не удаляй `canonical`, `og:*`, JSON-LD, `no-js`, семантическую разметку, `alt`, управление с клавиатуры и существующие контракты форм без явной причины.
- Интерактивные элементы должны иметь видимый `:focus-visible`, размер не меньше `--control-height`, понятное название действия и корректное состояние ошибки/успеха.
- Анимация допустима только если объясняет действие или поддерживает иерархию. Обязательно сохраняй `prefers-reduced-motion`; не добавляй постоянное движение ради эффекта.
- Для ссылок и ресурсов используй существующие локальные пути и проверяй, что они не ведут на `localhost`.

## Проверка результата

После изменений:

1. Запусти `npm run check`.
2. Если менялась разметка, CSS, JS или production-путь — запусти `npm run build`.
3. Для UI-изменений сгруппируй проверку и один раз проверь страницу в браузере на desktop и mobile. Оцени фактический render: иерархию, интервалы, типографику, переполнение, обрезание изображений, доступность меню и формы.
4. Не запускай глубокий performance/DOM/network-аудит без признаков проблемы.
5. Если найден очевидный визуальный дефект, исправь его и повтори только необходимую проверку. Если остаётся субъективный спор о направлении, остановись и спроси пользователя.

В финале сообщи, какие файлы изменены, какие проверки прошли и что осталось неизвестным или требует решения пользователя.

## Работа с текущим состоянием Git

Рабочее дерево может содержать изменения пользователя. Перед правками проверь `git status` и не удаляй, не откатывай и не форматируй чужие изменения. Не используй `git reset --hard`, `git checkout --`, массовое удаление или перезапись файлов без явного запроса.

Изменяй минимальный набор файлов, относящихся к задаче. Если обнаружил конфликт с уже изменённым файлом, сначала сообщи об этом и отдели свой патч от чужой работы.
