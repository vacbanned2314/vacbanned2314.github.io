## Правила работы над редизайном

1. Перед существенными изменениями сначала изучай существующую страницу, компоненты, стили и связанные файлы.
2. Если задача допускает несколько существенно разных решений по UI/UX, визуальному направлению, структуре страницы или поведению — сначала задай мне конкретные уточняющие вопросы.
3. Не принимай молча существенные продуктовые или дизайнерские решения.
4. Не задавай вопросы по очевидным implementation details, которые можно безопасно определить из существующего codebase.
5. При полном редизайне страницы сначала предложи 2–3 визуальных направления и объясни различия. Не начинай полную реализацию, пока я не выберу направление.
6. Основная цель сайта «Теплоремсервис» — получение обращений на установку и обслуживание отопления и автоматики. Визуальные решения должны в первую очередь усиливать доверие, понятность услуг и конверсию, а не декоративность.
7. Избегай generic AI/SaaS aesthetics. Сайт должен восприниматься как сайт компетентной инженерной компании.
8. Сохраняй визуальную консистентность между страницами. Используй существующую дизайн-систему или обновляй её централизованно, а не создавай локальные стили без необходимости.
9. После существенных визуальных изменений проверяй страницу в браузере на desktop и mobile и исправляй обнаруженные визуальные проблемы.

## Обязательная браузерная проверка UI-изменений

Для любых изменений, влияющих на UI, layout, typography, responsive или визуальное поведение, учитывай стоимость browser-проверок и группируй связанные изменения.

- Не используй браузер после каждой мелкой визуальной правки.
- Во время реализации группируй связанные UI/CSS-изменения и проверяй их одним проходом.
- Для существенных изменений UI перед завершением задачи обязательно запусти локальный сайт и выполни одну browser-проверку.
- По умолчанию проверь только 2 viewport: один desktop и один mobile.
- Сначала оцени фактический render визуально: layout, hierarchy, typography, spacing, overflow, clipping, responsive и очевидные визуальные дефекты.
- Не выполняй глубокий DOM/CDP/network/performance audit без причины.
- Console проверяй только если есть признаки runtime-проблемы или изменение затрагивает JS/интерактивность.
- Если первая browser-проверка не выявила существенных проблем, заверши задачу без дополнительных итераций.
- Если обнаружен реальный визуальный дефект, исправь его и выполни только необходимую повторную проверку.
- Не делай дополнительные screenshots/viewports/итерации только ради формальной самопроверки.
- Если дальнейшая визуальная доработка субъективна, а не является очевидным дефектом, не расходуй дополнительные итерации — покажи результат мне и запроси решение.

Не изменяй дизайн только ради прохождения формальной проверки. Если результат спорный с точки зрения визуального направления или UX — сначала спроси меня.
